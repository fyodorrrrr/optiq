## Executive summary

Seven findings: **P0: 0; P1: 1; P2: 5; P3: 1**.

Priorities:

1. Keep keyboard focus visible while a drawer covers the page.
2. Put mobile completion and error feedback near the action that caused it.
3. Validate the combined resize limit and explain how to correct it.
4. Give mobile diagram annotations a readable minimum size.

## Detailed findings

### 1. [P1] Keyboard focus escapes behind the mobile drawer

- **Category:** Accessibility.
- **Location:** [DetailsDrawer.tsx](../../frontend/src/components/lab/DetailsDrawer.tsx), lines 10–19; [LabUI.css](../../frontend/src/components/lab/LabUI.css), line 281.
- **Reproduction:** At 390px, open Image details. Focus correctly moves to Close details. Tab moves to Back to the experiment; another Tab moves to a page control outside the drawer while the full-width drawer stays open. With a result present, Result PNG and Run details receive hidden focus. Without a result, Back to settings receives it.
- **Impact:** Keyboard users can operate controls they cannot see. Escape and close-button focus return work, but do not prevent this failure.
- **Standard:** WCAG 2.2, 2.4.11 Focus Not Obscured (Minimum).
- **Recommendation:** On narrow screens, use dialog semantics, background inertness, and contained focus for the full-width sheet. If retaining a nonmodal desktop drawer, dismiss it or otherwise keep newly focused background controls visible. Preserve Escape and return-to-trigger behavior.
- **Suggested command:** `$impeccable harden`.
- **Evidence:** `/private/tmp/lab1-audit-focus-hidden.png`; the drawer remained open while focus was outside it and obscured.

### 2. [P2] Mobile completion and error feedback is far from the action

- **Category:** Responsive design / Accessibility.
- **Location:** [Lab1.tsx](../../frontend/src/labs/lab1/Lab1.tsx), lines 54–65 and 89–100; [LabUI.css](../../frontend/src/components/lab/LabUI.css), lines 94 and 111.
- **Evidence:** At 390 × 844 after Inspect pixel, the run button's viewport top was about 797px, the result summary 1,073px, the actual pixel neighborhood 2,047px, and completion status 2,400px. An invalid upload's alert also appeared below the image/zoom stack. Focus did not move to an error or result.
- **Impact:** A sighted mobile user can finish an operation without seeing what happened. Inspection is particularly affected because the full original and unchanged result precede the useful numerical neighborhood.
- **Standard:** Usability finding; live regions exist, and screen-reader announcement behavior was not manually evaluated.
- **Recommendation:** Add a brief local run state and completion message beside the action, with a View result link that targets the operation's useful output. Put upload failures beside upload actions and link validation errors to their fields. Preserve detailed results and existing previous-result labels.
- **Suggested commands:** `$impeccable adapt`, `$impeccable harden`.

### 3. [P2] Resize accepts a dimension pair that the server must reject

- **Category:** Implementation integrity / Accessibility.
- **Location:** [Controls.tsx](../../frontend/src/labs/lab1/Controls.tsx), lines 20–21; [useLab1.ts](../../frontend/src/labs/lab1/useLab1.ts), lines 141–168.
- **Reproduction:** Disable Keep aspect ratio, enter 4096 for width and height, and run. Both individual HTML fields accept the values. The API returns 422: “Images must be at most 4096px per side and 4 million pixels total.” No field receives `aria-invalid`, an associated correction hint, or focus.
- **Impact:** The error is accurate, but students must discover the combined limit after a failed request and work out which values to change.
- **Standard:** Error-prevention and recovery finding; not a blanket claim that existing native numeric validation fails.
- **Recommendation:** Validate `width * height <= 4_000_000` before submission; show the combined limit with the dimension fields, associate the message, and focus the relevant field. Keep backend validation authoritative.
- **Suggested command:** `$impeccable harden`.

### 4. [P2] Learning diagram labels shrink below a comfortable reading size

- **Category:** Responsive design.
- **Location:** [LearningFigure.tsx](../../frontend/src/labs/lab1/LearningFigure.tsx), line 30; [LabUI.css](../../frontend/src/components/lab/LabUI.css), lines 268–271 and 307–313.
- **Evidence:** The SVG uses a 460-unit-wide viewBox with 16-unit text. Measured screen transforms produce approximately 12.5px labels at 390px, 10.0px at 320px, and 11.4px at 720px while the two-column layout remains active.
- **Impact:** The page avoids overflow by shrinking the information students need to read, especially BGR values and array indexing.
- **Standard:** Readability finding. WCAG does not specify a universal minimum font size; this alone is not an automatic AA failure.
- **Recommendation:** Move key annotations into responsive HTML, or supply a stacked diagram composition for small screens. Stack the canvas earlier on tablets. Aim for 14–16px annotation text without shrinking the whole figure.
- **Suggested command:** `$impeccable adapt`.
- **Evidence:** `/private/tmp/lab1-audit-canvas-320.png`.

### 5. [P2] Navigation links have small mobile tap areas

- **Category:** Responsive design.
- **Location:** [LabPage.tsx](../../frontend/src/components/lab/LabPage.tsx), lines 15 and 18.
- **Evidence:** All labs and the header How it works links measure about 21px tall; Back to labs is about 17px tall. The main experiment buttons, drawer close action, and next-lab action already have larger targets.
- **Impact:** Frequent navigation is less comfortable to tap than the experiment controls.
- **Standard:** Below the skill's 44px touch-target guideline. Not asserted as a WCAG 2.5.8 failure: spacing/inline exceptions require separate assessment.
- **Recommendation:** Expand the links' hit areas with padding/min-height while retaining their current quiet visual weight. Keep sufficient separation.
- **Suggested command:** `$impeccable adapt`.

### 6. [P2] Failed image replacement does not identify the retained source

- **Category:** Implementation integrity.
- **Location:** [useLab1.ts](../../frontend/src/labs/lab1/useLab1.ts), lines 40–59 and 74–86; [Lab1.tsx](../../frontend/src/labs/lab1/Lab1.tsx), lines 69–88.
- **Reproduction:** With the color sample loaded, request the grayscale sample and return a 503 from that sample request. The previous color image remains visible and runnable. Its stored source name is not shown in the interface, and the failure does not explicitly say the old source was retained.
- **Impact:** Retaining a usable image is helpful, but the user must infer which input a later run will use.
- **Recommendation:** Display the filename/sample name next to Original. On a failed replacement, say that the previous named image is still loaded. Keep successful source replacement clearing stale results as it does now.
- **Suggested commands:** `$impeccable clarify`, `$impeccable harden`.

### 7. [P3] Opening Lab 1 loads every lab's frontend code

- **Category:** Performance.
- **Location:** [App.tsx](../../frontend/src/App.tsx), lines 5–11.
- **Evidence:** All seven lab routes are statically imported. The production build produces one main 414.78 kB JavaScript bundle (126.26 kB gzip), plus 50.70 kB CSS (10.17 kB gzip).
- **Impact:** Lab 1 pays the initial download/parse cost of unrelated labs. No observed performance threshold failure was established; this is an optional improvement.
- **Recommendation:** Consider route-level lazy imports with an accessible loading fallback when optimizing delivery. Do not add memoization or image lazy loading indiscriminately to the initial experiment previews.
- **Suggested command:** `$impeccable optimize`.

## Patterns and systemic issues

- Drawer opening and closing are centralized, but focus visibility across the entire open lifecycle is not. Fixing the shared component benefits all its uses.
- Completion and errors are concentrated below outputs rather than at the action that generated them. This becomes most apparent when columns stack.
- Viewport fit is currently stronger than content readability: no overflow does not guarantee readable diagrams or useful feedback placement.

## Positive findings

- All six operations ran against the actual backend and returned HTTP 200 with expected array shapes: inspect/edit 480 × 640 × 3, grayscale 480 × 640, crop/resize 240 × 320 × 3, rotation 640 × 480 × 3.
- No horizontal page overflow at 1440, 1360, 1359, 1024, 768, 720, 390, or 320px.
- Full-height settings backgrounds, normal button sizing, and drawers that do not expand workspace height address the previously observed layout problems.
- Pixel clicking has keyboard-accessible coordinate-field equivalents. Selection is also described textually.
- Diagrams have meaningful accessible descriptions and are explicitly illustrative rather than presented as computation on the user's image.
- Core palette contrast is strong: charcoal/white 17.93:1; secondary gray/off-white 5.43:1; green/white 7.54:1. Intentional diagram colors are data, not an interface-token defect.
- Reduced-motion emulation changes document scrolling to `auto`; forced-colors inspection retained readable text and the diagram's meaningful colors.
- Abort controllers, cancellation messaging, retained-result labels, bounded uploads, and parameter provenance provide a useful foundation.
- ESLint and production TypeScript/Vite build pass. No uncaught page JavaScript errors occurred during the audit.

## Automated checks and limitations

Four axe scans (desktop initial, desktop rotation result, desktop image drawer,
and mobile) returned **zero definite violations**. They also returned checks
requiring review, notably SVG/drawer contrast and naming on `#lab-results`.
Those incomplete checks are not counted as confirmed violations. Core text
contrast was checked separately; results-region semantics should receive a
manual screen-reader pass.

The detector returned no findings, so there are no detector false positives
to dismiss. Manual findings above remain valid despite the clean detector.

Browser testing used headless Chromium/Brave. VoiceOver/NVDA, Safari/Firefox,
physical touch devices, real browser zoom, slow-device profiling, and a
production deployment were not tested. Width 720px is a reflow check, not a
claim that actual 200% browser zoom was tested. API failures/delays used
explicit browser request interception; successful operations used real
computation. No backend algorithm changes or fixes were made.
